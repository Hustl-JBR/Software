# UI parity audit

Audited 2026-08-01 against the approved `atlas-north` demo and the authenticated `atlas-staging` Railway application. The demo is the visual baseline; PostgreSQL, Better Auth, organization authorization, server commands, idempotency, and audit controls are the staging technical baseline.

## Executive finding

Atlas currently shares global CSS and a few intake/load primitives, but not a coherent product shell. Demo routes render the approved navigation and feature workspaces from browser-session state. Staging renders a one-link shell, a sparse command page, and a monolithic `/staging` form collection. Several polished routes are effectively demo-only because their components read `OperationsDemoProvider` directly. Staging already has enough real data for a strong command center, loads table, load operations, manual tracking, carrier directory, users/settings summary, communications, tasks, and audit history. It does not yet have persisted document metadata, carrier master profiles, facility/customer master records, live GPS, financial ledgers, notification policies, or AI recommendations.

The recommended unification is a shared shell plus typed view models. Demo and staging providers may assemble different data, but shared page components must not import Prisma or demo providers.

## Data-provider boundary

Target flow:

```text
Demo browser-session provider ─┐
                              ├─> typed Atlas view models ─> shared workspace components
Staging server repositories ──┘
```

Shared components must receive serializable view models and action URLs/forms. They must not import Prisma, `OperationsDemoProvider`, or environment variables. Staging loaders remain server components and tenant-scope every query. Demo adapters may continue reading the browser-session provider.

## Staging truthfulness rules

- Never render demo arrays, simulated movement, synthetic financial metrics, AI recommendations, or performance statistics in staging.
- Label tracking `Manual tracking — no live GPS connected`.
- Label carrier evidence `Manual staging review — no FMCSA provider connected`.
- Render missing document storage, recovery delivery, policies, analytics, and integrations as controlled inactive states.
- Use only the small synthetic operations-drill dataset in the staging database; test identities and businesses must remain visibly synthetic.
- Do not expose seed variables, infrastructure instructions, or credential setup on authentication screens.

## Implementation sequence

1. Shared mode-aware shell, navigation, page heading, badges, empty/loading/error primitives, and sign-in.
2. Staging command-center view model and shared command-center composition.
3. Shared loads table and staging load-operations tabs using real PostgreSQL data.
4. Real manual tracking, Network/carrier review, Documents empty state, Analytics summary, and Settings/users views.
5. Small idempotent staging drill seed expansion only where existing schema supports it.
6. Demo/staging browser comparison, narrow-width review, console review, and regression suite.
